# Local Factory runbook

[Documentation](../INDEX.md) / [Operations](README.md) / Local Factory runbook

Reviewed against source on 2026-10-03. Commands below describe the current implementation. No live
start, incident recovery, backup restore or release deployment was performed when writing this
guide. Shared constraints and process remain authoritative in [MODEL](../technical/MODEL.md),
[WORKFLOW](../technical/workflow/WORKFLOW.md) and [CLAUDE.md](../../CLAUDE.md).

## Prerequisites

Use a Linux workstation with Bash, Git, CMake 3.16 or later, a C++17 compiler, Boost.System,
pkg-config and libglog. The runner also uses Linux `/proc`, `ss`, `setsid` and `nproc`. The client
needs Node.js and npm compatible with its [package](../../client/web/package.json) and lockfile.
The [CMake definition](../../server/CMakeLists.txt) and [build scripts](../../build.sh) define
the actual build requirements.

Agent work additionally needs Bubblewrap and the manifest-declared agent executables, credentials
and workspace toolchains. Check the resolved manifest and its warnings before starting a lane;
host installation alone does not make a tool reachable inside a confined lane. See
[confinement](../../server/design/lane-confinement.md) and
[agent startup](../../server/design/agent-session.md).

Tests need Python 3, pytest and the imports used by the [server fixtures](../../server/tests/conftest.py).
The browser gate additionally needs its supported Chrome/Chromium installation and the utilities
used by the [gate runner](../../client/web/gate/run-gate.sh). These are separate from the ability
to compile or open the development client.

## Build and start

Run from the Factory checkout:

```bash
./build.sh build
./build.sh run "$PWD" --no-open
```

`build` compiles both halves. The root script runs `npm ci` when client dependencies are absent or
the lockfile changed. `run` builds the server and starts it with the explicit repository root;
it starts the web client through `npm run dev`. Open <http://localhost:7779>. The client proxies
API and socket traffic to the server, whose default HTTP port is 7777. The script accepts
`FACTORY_HTTP_PORT` and `FACTORY_WEB_PORT` when a separate instance needs different ports.

Server build and test outputs live in the ignored `.cache/server/` directory at the checkout
root: `build/` contains the release binary, `build-tsan/` contains the ThreadSanitizer build, and
`pytest/` contains pytest's cache. Run `server/build.sh clean` to remove the release build, then
`server/build.sh build` to recreate it. Each checkout has its own generated files.

TypeScript's incremental build state lives in `.cache/client/`. The root test runner and soak
runner use `.cache/python/` for Python bytecode. For direct Python commands, set an absolute
`PYTHONPYCACHEPREFIX` inside this checkout to select the same cache. The shared VS Code settings
use the server's cache build directory and hide generated bytecode folders from the Explorer.

To manage another repository, pass that repository's absolute root instead of `"$PWD"`. Its
`.factory/factory.json` determines the documents and workspaces you will see. A missing ticket in
another instance is not evidence that the ticket disappeared.

The runner can stop a previous matching process from the same checkout when reclaiming its ports.
Inspect active lanes before restarting an existing instance. It refuses a port held by a process
it cannot identify as its own; use the printed identity to diagnose that conflict. Starting this
runner is not a packaged production deployment, and a successful web build does not change that.

## Read-only checks

For default ports, these requests inspect the running instance without starting an agent:

```bash
curl --fail-with-body --silent --show-error http://localhost:7777/api/health
curl --fail-with-body --silent --show-error http://localhost:7777/api/manifest
curl --fail-with-body --silent --show-error http://localhost:7777/api/lanes
curl --fail-with-body --silent --show-error http://localhost:7777/api/runs
```

Check the returned document root and Git root against the intended repository. Health answers
liveness and repository identity; the current constant version field does not identify the
compiled source SHA. The resolved manifest is the place to inspect validation errors, path
warnings, declared commands and profiles. Exact response shapes belong to the
[HTTP schema](../technical/contracts/http.schema.json) and [registered handlers](../../server/app/api/manager.h).

The Home and Lanes surfaces show work needing attention, process state, seats and resources. Runs
and ticket reports supply the relevant transcript and evidence. The socket status matters: a
browser showing its last answer while disconnected does not establish current server state.
The Delivery surface's process metrics are useful evidence about work; do not interpret them as
an uptime monitor or release readiness certificate.

## Stop and restart

Before a planned stop, inspect lanes and pending approvals, save evidence and account for active
work through the tool. Use the existing controls and shared workflow for any run or lane action;
this guide does not authorize releasing work just to make a restart convenient. Once work is
accounted for, Ctrl-C in the terminal running `./build.sh run` stops its server and web process
groups. That cleanup is not an assurance that every agent conversation can resume afterwards.

On the next start, check health identity and compare the lane set, warnings and resources with
the pre-stop capture. The server reads persisted lane records and adopts eligible registered lane
worktrees. Adoption is a survey of existing work, not an automatic restart of agent work.

The current [lane persistence implementation](../../server/app/lane/store.cpp) records lane
identity, ticket, workspace, role, branch, worktree, claim time and PID. It does not serialize
resource holdings or the resource queue. A surviving PID or recovered checkout does not prove
that resource exclusivity or session control survived the restart. An adopted record can also
lack a workspace. Investigate these differences before starting competing work.

Declared-command output is retained by the current browser socket service, rather than a server
command-output ledger; a new browser session may lose it. Save relevant command captures to the
repository's evidence locations as the shared workflow requires.

## Troubleshooting and incidents

| Symptom | First evidence to inspect | Next step |
|---|---|---|
| Client cannot connect | Runner output, health response, socket status and configured ports | Establish which half exited and which instance owns the port before another start. |
| Wrong or missing backlog | Health roots and resolved manifest document paths | Point the instance at the intended document root and inspect manifest errors. |
| Lane cannot start | Named API refusal, selected profile, declared toolchain, readiness/preflight capture | Read the capture linked by the refusal; fix its declared dependency rather than broadening access. |
| Agent appears idle or blocked | Lane state, pending permission request, last words and run transcript | Distinguish an ended turn, approval wait and crashed process before acting. |
| Resources remain held or lanes differ after restart | Pre-stop lane capture, current `/api/lanes`, startup recovery warnings | Reconcile through tool-owned lane/resource state before admitting more work. |
| Landing is refused | Ticket delivery detail and lander output | Inspect conflicting paths or missing QA session evidence; preserve the operator checkout. |

Retain the timestamp, repository roots, source commit if known, exact action, full error and
relevant run/capture paths. Use [known limitations](KNOWN-LIMITATIONS.md) as documented history
and confirm the current symptom against its evidence. Applicable workflow failures follow the
existing [readiness cause process](../technical/workflow/WORKFLOW.md#known-failures-and-run-readiness); escaped defects
follow the [escape ledger](ESCAPES.md). Do not turn an operational symptom into an invented
PASS or a new policy in this guide.

The [lane ownership rule](../../CLAUDE.md#lanes--never-remove-a-checkout-without-asking-the-tool)
and [MODEL S5](../technical/MODEL.md#s5--exclusivity--one-holder-and-one-authority-on-who-holds) still apply.
Git cleanliness cannot establish whether a lane is live. If the tool cannot answer, that
uncertainty is not permission to delete its checkout or state. Preserve local work and diagnose
ownership before using the tool's supported recovery or release controls.

## Checks and VERIFY

`./build.sh test` runs the server pytest suite and client Vitest suite. It does **not** run the
browser gate. Before server checks, build the current binary rather than checking an older build.

The shared [VERIFY procedure](../tickets/_TEMPLATE.md) runs after merge on `main`; its browser
sweep is unscoped. The following commands identify the two runners involved, rather than replace
the ticket's complete procedure:

```bash
cd server
python3 -m pytest tests/ -v
```

```bash
cd client/web
npm run gate
```

The browser gate builds the client, validates the fixture server and drives the declared surfaces
in both themes. A fixture gate remains separate from the required real-repository user journey.
Document changes also require the shared document gate. Keep command captures and report any
unexecuted, failed or scoped-out checks accurately.

## Backup and restore draft

This is a proposed checklist for a future operating procedure. No backup job, retention period,
recovery target or successful restored copy is established by this document.

| State | Preservation needed |
|---|---|
| Code, product documents, tickets, reports, schemas and manifest | Git history covers committed files. Include all refs that hold unlanded work, plus uncommitted and untracked files; a fresh clone from the remote alone may omit these. |
| `.factory/runs/` | Local run metadata, transcript evidence and preflight captures are not recovered by restoring committed documents. |
| `.factory/lanes/` and `.factory/worktrees/` | Lane records reference local paths and PIDs. Worktrees contain working files and depend on Git worktree metadata; directory copying alone is not a complete Git recovery plan. |
| `.factory/permissions.json` and `.factory/ids.json` | Local permission grants and allocation state need an explicit retention and restore decision. Restored permissions must be reviewed for the destination environment. |
| Live processes, pending approvals, resource queue and browser command output | Do not assume these survive a file backup. They require reconciliation or separately retained evidence. |

Proposed backup sequence:

1. Record source commit, document/Git roots, manifest, lane/resource state and unlanded refs.
2. Account for active writers through the tool; define a consistent snapshot point. Preserve
   uncommitted work before any stop. Do not copy changing runtime files and call the copy verified.
3. Preserve Git repository metadata, worktree metadata and working files together with the local
   runtime records. Identify linked repositories and locally retained evidence that must be covered.
4. Specify destination access, retention, checksum verification and ownership before scheduling a
   backup. Credentials need their own explicit handling; this checklist does not include them by default.

Proposed restore drill:

1. Restore into an isolated location with no active agents, then inspect Git/worktree integrity and
   document links before opening the copy with Factory.
2. Review absolute manifest paths, permission grants and lane records. Old PIDs are not portable
   process identities; prevent a restored copy from treating the original instance's processes as its own.
3. Use distinct ports, verify health roots, and compare tickets, reports, transcripts and lane
   warnings against the backup inventory. Reconcile resources before starting any agent.
4. Retain the restore command captures, missing items and elapsed recovery time. Only a completed
   drill can establish the backup's recoverability; none has been performed for this draft.
